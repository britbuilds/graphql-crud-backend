# GraphQL CRUD Backend (Go + Postgres)

A starter backend you can copy for any project that needs a database and a GraphQL API.
It comes with one example resource, `media`, that has full create, read, update and delete.

```
Browser / app ──GraphQL──▶ Go server (gqlgen) ──▶ Go queries (sqlc) ──▶ PostgreSQL (Docker)
```

| Tool | Job |
|---|---|
| **Docker** | Runs Postgres on your machine |
| **goose** | Migrations: changes to the database structure, kept as numbered files |
| **sqlc** | Turns the SQL in `db/queries.sql` into Go functions |
| **gqlgen** | Turns `graph/schema.graphqls` into a GraphQL server |

---

## Requirements

- [Go](https://go.dev/dl/) (version in `go.mod` or newer)
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) (must be **running**)

The commands below are for **PowerShell on Windows**.

---

## Quick start

```powershell
# 1. Start Postgres
docker compose up -d

# 2. Download Go dependencies
go mod tidy

# 3. Create the tables
./migrate.ps1 up

# 4. (Optional) add example data
./seed.ps1

# 5. Start the server
go run .
```

Open **http://localhost:8080** for the GraphQL Playground and try:

```graphql
query {
  mediaList { id title type }
}
```

If PowerShell says *"running scripts is disabled"*, run this once:
`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`

## Project structure

```
db/
  migrations/        ← database changes (goose). One file per change.
  queries.sql        ← every SQL query the app uses (sqlc reads this)
  seed.sql           ← example data
graph/
  schema.graphqls    ← the GraphQL API: types, queries, mutations   (you edit)
  schema.resolvers.go← code that runs for each query/mutation       (you edit)
  convert.go         ← converts between database and API types      (you edit)
  resolver.go        ← gives resolvers access to the database       (you edit)
  generated.go, model/  ← generated by gqlgen, never edit
internal/db/         ← generated by sqlc, never edit
main.go              ← starts the server
docker-compose.yaml  ← Postgres container settings
migrate.ps1 / generate.ps1 / seed.ps1  ← shortcut scripts
```

## Everyday commands

| Command | What it does |
|---|---|
| `docker compose up -d` | Start Postgres (in the background) |
| `docker compose down` | Stop Postgres. **Data is kept.** |
| `docker compose down -v` | Stop Postgres **and delete all data** (full reset) |
| `./migrate.ps1 up` | Apply all new migrations |
| `./migrate.ps1 down` | Undo the most recent migration |
| `./migrate.ps1 status` | Show which migrations have been applied |
| `./migrate.ps1 create add_something sql` | Create a new, numbered migration file |
| `./generate.ps1` | Regenerate Go code (runs sqlc, then gqlgen) |
| `./seed.ps1` | Load example data from `db/seed.sql` |
| `go run .` | Start the server on http://localhost:8080 |
| `go mod tidy` | Add or remove Go dependencies to match your imports |

Restart the server (**Ctrl+C**, then `go run .`) after changing any Go code.

## How migrations (goose) work

Think of it as **git for your database structure**. Each change is a numbered file in `db/migrations/`:

```
00001_create_media.sql
00002_add_score.sql
```

Each file has an **Up** part (make the change) and a **Down** part (undo it):

```sql
-- +goose Up
ALTER TABLE media ADD COLUMN score INT;

-- +goose Down
ALTER TABLE media DROP COLUMN score;
```

- goose remembers which files it has already run, so `up` only runs the new ones.
- `down` undoes **one** migration, the most recent. Careful: undoing a `CREATE TABLE` deletes that table and its data.
- **Never edit a migration that has already run.** Add a new file instead.
- sqlc reads this folder too, so your Go code always matches the database.

## Recipes

### Add a column to an existing table

1. `./migrate.ps1 create add_score_to_media sql`, then fill in the Up and Down parts of the new file.
2. `./migrate.ps1 up`
3. Add the field to the type in `graph/schema.graphqls` (and to the input types if clients should be able to set it).
4. `./generate.ps1`
5. Map the new field in `graph/convert.go` (`toGQLMedia`), and in the create/update resolvers if it's in the inputs.
6. Restart the server.

### Add a new query or filter

1. Add the SQL to `db/queries.sql` with a name comment:
   ```sql
   -- name: ListMediaByYear :many
   SELECT * FROM media WHERE release_year = $1 ORDER BY id;
   ```
   `:one` = one row, `:many` = a list, `:exec` = no result, `:execrows` = number of rows changed.
2. Add the field to `type Query` in `graph/schema.graphqls`.
3. `./generate.ps1`
4. Fill in the new function in `graph/schema.resolvers.go` (it starts as `panic("not implemented")`).
5. Restart the server.

### Add a whole new table (a new resource)

Follow the `media` example. For a `users` table:

1. **Migration:** `./migrate.ps1 create create_users sql` with `CREATE TABLE users (...)` in Up and `DROP TABLE users;` in Down. Then `./migrate.ps1 up`.
2. **Queries:** add `GetUser`, `ListUsers`, `CreateUser`, `UpdateUser`, `DeleteUser` to `db/queries.sql` (copy the media ones and rename them).
3. **Schema:** add `type User`, `input CreateUserInput`, `input UpdateUserInput`, and the new fields under `type Query` and `type Mutation`.
4. `./generate.ps1`
5. **Convert:** add a `toGQLUser` function in `graph/convert.go`.
6. **Resolvers:** fill in the new functions in `graph/schema.resolvers.go`.
7. Restart the server.

Once a project has a few tables, you can split `db/queries.sql` into a folder (`db/queries/users.sql`, `db/queries/media.sql`). Set `queries: "db/queries/"` in `sqlc.yaml`.

## Starting a new project from this template

1. Copy the folder and rename it.
2. **Go module name:** change the first line of `go.mod` (`module graphql-crud-backend`), then find and replace `graphql-crud-backend/` in all `.go` files.
3. **Database name:** replace `appdb` in `docker-compose.yaml`, `main.go`, `migrate.ps1` and `seed.ps1`.
4. Remove or replace the `media` example (migration, queries, schema, resolvers, convert functions, seed).
5. Run `./generate.ps1`, then follow the Quick start.

---

## Settings

The server and `migrate.ps1` read the database address from the `DATABASE_URL` environment variable. If it isn't set, they use the local Docker database:

```
postgres://postgres:dev@localhost:5432/appdb
```

On a real server, set `DATABASE_URL` and you don't need any code changes.

## Troubleshooting

| Problem | Fix |
|---|---|
| `'docker' is not recognized` | Open Docker Desktop and wait for "Engine running". Restart your editor if Docker was just installed. |
| `relation "media" does not exist` | The table isn't in this database. Run `./migrate.ps1 up`. If you created tables from your editor's database tool, check it's connected to `appdb`, not `postgres` (`SELECT current_database();`). |
| `column "x" does not exist` | You added it to the code but not the database. Write a migration and run `./migrate.ps1 up`. |
| `database "appdb" does not exist` | Postgres only creates it the first time the container starts. Reset with `docker compose down -v` then `docker compose up -d` (this deletes data). |
| Queries return `[]` | The table is empty. Run `./seed.ps1` or add data with a mutation. |
| New field not showing in Playground | Run `./generate.ps1`, restart the server, then refresh the Playground page. |
